# Recipe — CWE-89 (SQL Injection)

## When to apply this recipe

The vulnerability says user-controlled input is being concatenated into a
SQL string. Common shapes:

- String concat: `"SELECT * FROM x WHERE y = '" + req.query.y + "'"`
- Template literal: `` `SELECT * FROM x WHERE y = '${req.query.y}'` ``
- `sprintf`/`%s`-style formatting passed to `db.query`
- ORMs called with raw SQL (`Sequelize.query(rawSql)`, `knex.raw(rawSql)`)

## Fix pattern — parameterized queries

Use the driver's bind-parameter syntax. The driver sends the SQL and the
values as separate fields to the database; the database never parses user
input as SQL.

| Driver | Placeholder | Pass values via |
|---|---|---|
| `sqlite3` (Node) | `?` | `db.all(sql, [v1, v2], cb)` |
| `pg` (Node) | `$1`, `$2` | `client.query(sql, [v1, v2])` |
| `mysql2` (Node) | `?` | `conn.execute(sql, [v1, v2])` |
| `psycopg2` (Python) | `%s` | `cur.execute(sql, (v1, v2))` |
| `sqlite3` (Python) | `?` | `cur.execute(sql, (v1, v2))` |
| Sequelize | `:name` | `query(sql, { replacements: { name: v } })` |
| Knex.js | `?` | `knex.raw(sql, [v1])` or use the builder |

**Wildcards in LIKE clauses go in the value, not the SQL.** Write:

```javascript
db.all('SELECT * FROM products WHERE name LIKE ?', ['%' + q + '%'], cb);
```

NOT:

```javascript
db.all("SELECT * FROM products WHERE name LIKE '%" + q + "%'", cb);   // still vulnerable
```

## Canonical diff (juice-shop-extensions seeded vuln #2)

Before:

```javascript
router.get('/search', (req, res) => {
  const q = req.query.q || '';
  const sql = "SELECT id, name, price FROM products WHERE name LIKE '%" + q + "%'";
  db.all(sql, (err, rows) => {
    if (err) return res.status(500).json({ error: err.message });
    res.json(rows);
  });
});
```

After:

```diff
 router.get('/search', (req, res) => {
   const q = req.query.q || '';
-  const sql = "SELECT id, name, price FROM products WHERE name LIKE '%" + q + "%'";
-  db.all(sql, (err, rows) => {
+  const sql = 'SELECT id, name, price FROM products WHERE name LIKE ?';
+  db.all(sql, ['%' + q + '%'], (err, rows) => {
     if (err) return res.status(500).json({ error: err.message });
     res.json(rows);
   });
 });
```

No new dependency needed — `sqlite3`'s `db.all` already supports
parameter binding.

## Verification

- Payload `?q=' UNION SELECT * FROM users--` should return zero rows
  (matching a product literally named that string), NOT exfiltrate the
  users table.
- The legitimate search path still returns results: `?q=Apple` returns
  products with "Apple" in the name.
- Project tests still pass.

## Things to watch for

- If the file has multiple SQL queries built the same way, fix them ALL
  in one PR.
- Identifiers (table names, column names) CANNOT be parameterized —
  drivers only bind values. If the vulnerable input is a column or table
  name (rare but happens in admin tools), the fix is an allowlist:
  ```javascript
  const ALLOWED_COLUMNS = new Set(['name', 'price', 'created_at']);
  if (!ALLOWED_COLUMNS.has(req.query.sort)) {
    return res.status(400).json({ error: 'invalid sort column' });
  }
  const sql = `SELECT * FROM products ORDER BY ${req.query.sort}`;  // safe now
  ```
- ORM `findOne({ where: { name: req.query.q } })` calls are already
  parameterized — no fix needed. Don't "defensively rewrite" code that
  was already safe.

## Stop conditions

- The query is generated by a query builder you don't understand
  (Sequelize raw, complex Knex chains). Stop and ask the dev to confirm
  the proposed fix — the wrong rewrite can change query semantics.
- The vulnerable input feeds a stored procedure call where the procedure
  itself does dynamic SQL. The fix belongs in the proc, not in the
  application code. Surface that to the dev.

## Test generation (T7 — differential regression test)

Pin the fix so the SQLi can't return. The generated test must **fail on the
pre-fix commit and pass on the post-fix commit** (Step 8b validates this).

- **Security exploit-as-test (preferred):** if a T9 exploit case exists for this
  finding, use the runnable test file it emitted (`torana pentest run --emit-test`).
  It fires the benign boolean/marker injection against the reaching request and
  asserts a SAFE response (no `SQL syntax` error, no tautology-widened result set).
- **Otherwise author one:** send the injecting input (`x' OR '1'='1' -- <marker>`)
  to the reaching handler and assert the response does NOT reflect a SQL error and
  does NOT return more rows than the benign control input. Assert the parameterized
  path is taken (e.g. the query is bound, not string-built) if unit-testable.
- Differential check: on the pre-fix commit the injection widens/error; post-fix it
  is neutralized. If it doesn't fail pre-fix, the test doesn't exercise the sink →
  `TEST_STATUS=uncovered`, do not commit.
